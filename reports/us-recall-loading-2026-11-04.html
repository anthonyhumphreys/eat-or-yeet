Validation: production build, typecheck and lint passed; 805 unit tests and 116 mobile/desktop browser checks passed. Six Notion checks were skipped because that integration was not enabled. Historical measurements. These results were recorded before the newer indexed database browsing and product-name redesign were integrated from main. The integration preserves that newer implementation; these benchmark numbers describe the earlier measured build.

A smaller first page

The sampled US dataset contains 4,518 records. All contribute to search and facet calculations on the server; only the requested visible rows and compact count metadata reach the browser. There is no background download of the full regional snapshot.

The tradeoff is explicit

Filtering previously ran over a full in-browser snapshot. It now requests a compact JSON result page, so new searches need network access and take longer to return. Text entry stays immediate. Previous rows remain visible during loading, with interaction paused to prevent opening a stale result; errors retain those rows and offer retry.

The measured search update includes the 150 ms typing debounce, request time and browser automation overhead. It is not an INP measurement. It should be assessed separately from the substantial reduction in arrival time.

Measurement conditions and limits

Three fresh-browser samples before and after, using the production build, Pixel 7 viewport, 4× CPU slowdown, 80 ms latency and 200,000 bytes/second download throughput. Server data and publisher caches were warm, and optional analytics was declined. No competing browser suite ran during the measurements.

These are small-sample local diagnostics, not production Core Web Vitals. Cold data caches, deployed edge behavior, physical low-end devices, Safari and real-user interaction latency remain unmeasured. The initial JavaScript bundle is essentially unchanged; the gain comes primarily from removing the full data payload.

Complete results and complete counts

One query model

HTML and JSON browsing use the same query parser, search terms, hazard classification, filter rules and count calculation. Counts are computed over the complete eligible regional snapshot before visible rows are limited.

Facet rules are preserved

Each facet excludes its own selection when counting alternatives, as before. A notice appears once in the result list even when it belongs to several product types or categories; those badges can overlap.

Pages remain shareable

“Show more” preserves the cumulative page behavior: page 1 shows up to 40 records, page 2 up to 80. URLs restore search, filters and visible depth. Back navigation restores the matching query, page and count together.

One coherent response

Rows and facet totals arrive together. Each response replaces the displayed view rather than appending records from different snapshots. Superseded requests are cancelled, so an older response cannot overwrite a newer query.

Freshness remains checked

A bounded cache shares revision-pinned public snapshots in a server worker. The dataset revision is read on every request, and start/expiry boundaries are applied after caching. Failed snapshot reads are evicted so retry can recover.

Recoverable loading

Browse requests time out after 15 seconds. Failed updates preserve prior results and show a retry action instead of claiming there are no matches. Pagination keeps its keyboard focus and shows a loading label while waiting.

Counts with a little character

Waiting counts use a short three-dot wave, followed by a 240 ms settle of the real number. No random digits, partial-dataset totals, fake progress or artificial completion delay. Reduced motion leaves static feedback and readable counts.
